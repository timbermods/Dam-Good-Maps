# Integration proposals only

No production changes are made by this branch. Start with the saturation count and directional-loop expansion; consider the neighbour table only after its memory cost and target-browser measurements justify it. Defer the clearing and drought changes. [REPORT.md](REPORT.md) explains the evidence and [RESULTS.md](RESULTS.md) contains every measured case.

[proposed-core.patch](proposed-core.patch) is the exact combined proposal against the pinned `dev` revision. It changes only the proposed `water.ts` and `drought.ts` content, restores their production import paths, and passes `git apply --check`. It has **not** been applied. Regenerate it with `powershell -File propose.ps1`; the script writes and checks a patch without modifying production files. The standalone copies below separate the five steps for evaluation and incremental integration.

1. In `src/core/sim/water.ts`, replace only the interior case of `WaterSim.computeWn` with the eight explicit wet tests in `prototypes/saturation/water.ts`. Keep the boundary loop. This has no new allocation or lifetime rule.
2. Expand only outflow pass 1's four iterations, as in `prototypes/unroll/water.ts`. Keep the four blocks in −y, −x, +y, +x order, preserve blocked-direction zero writes, and use a local break where the original iteration continued. Do not unroll or rearrange any summation. Re-measure the larger function on each browser JIT.
3. Optionally, in `WaterSim`, add the constructor-built four-neighbour `Int32Array` from `prototypes/topology/water.ts`; replace the direction dispatch in flow pass 1 and the four neighbour calculations in depth pass 2. Keep direction order, all parentheses, the leading zero in contamination accumulation, all sums, clamping and casts unchanged. Build the table once per simulator, including warm-start and cycle instances. Do not cache floor heights or source properties, which can change independently. The cost is 16 bytes per tile, or 1 MiB per 256² instance; account for concurrent preview/validation instances.
4. Consider the previous-flow clearing change only if its standalone and combined benchmark is beneficial on the integration target. Skip a previous wet tile's clear only when it remains in the current wet set; still write zeros for every wet-to-dry transition. Do not move the active-list rebuild or any flow pass. The investigation uses the existing invariant `D[i] > 0` iff the tile is in the current wet list.
5. Consider `src/core/sim/drought.ts`'s pool-drop temporary only if repeated drought measurements justify it. Populate it after the complete index-ordered evaporation sum, using the original division-then-multiplication expression. Retain every pool label and tile iteration. The heap/flood work is unchanged, so a large drought speedup is not expected.

Integrate one change per commit and re-run the parity and performance suites on each cumulative result. The measured combined prototype includes all five changes; the two- and three-change prefixes are unmeasured combinations, so do not assign them the all-five speedup. Use the combined patch as a reference for the eventual cumulative diff, not as a second patch to apply over already-integrated changes. Proposed production tests should retain the 12 golden fixtures, explicit 1×N/N×1 and seep/dam transition coverage, generated `.timber` hash baselines and daily weather checkpoints. Do not update golden hashes to accept an optimization mismatch.

The canonical settle must continue to serve generation, background editor validation and export. Warm preview must remain history-dependent and must never become export input. Preserve 128/64-tick checks, their current thresholds, the four-day/one-day caps, and worker slicing/cancellation.

For a Weather view based on the original cycle model, retain its native 768 ticks/day and two substeps per tick. Keep cancellation and streaming as separate integration work: yield between slices and stream completed key days. That model updates soil every 16 ticks, which is already an approximation; changing that interval is a results change and outside this proposal. Profile full UI latency separately before claiming the editor's 2 s water-preview budget or a responsive multi-day Weather view.

The late-arriving `investigation/cycles-exact` branch changes this integration route: its `CycleModel` runs independent `GameWater` and `GameSoil` classes, with per-tick soil and different contamination/calendar/loading rules. The present core patch changes neither class, so it gives **no direct exact-weather speedup**. [EXACT-CYCLES.md](EXACT-CYCLES.md) profiles that implementation and checks its Node/Chromium checkpoints. Do not replace it with the faster original model or transplant this patch into it mechanically. Its neighbour table already exists; porting the saturation/unrolling ideas would be a new prototype with new exactness evidence. Keep both models' results distinct.

The [M9 pipeline measurements](M9-PIPELINE.md) apply this exact combined patch to the unchanged prototype generator. Charge every retry and rebuild to the candidate's roughly 6 s budget; a faster individual settle is not a whole-pipeline budget pass. Do not remove validation, shorten settles, or change retry/planner decisions to meet that budget under this proposal: those would change results. Any further reuse of settled state needs proof that every simulation input and checkpoint decision is identical.

For stacked-layer water, carry over the idea of stable, ordered connectivity first. The literal flat neighbour offsets, eight-cell saturation test, four-direction expansion and heightfield drought formula are not drop-in changes for caves or multiple water bodies at one `(x,y)`. [STACKED-LAYERS.md](STACKED-LAYERS.md) assesses each prototype, memory implications and required proofs. Establish the new solver's reference semantics before measuring a topology cache or fixed-stencil fast path. No current speedup is a 3D performance claim.

Before integrating, rerun the complete parity suite on the actual cumulative production change, run the repository's normal unit/contract and determinism checks, and repeat the 128²/256² performance measurements. The investigation's Node/Chromium proof is complete for its pinned prototypes; Firefox and WebKit remain additional repository determinism gates. This branch is an open, unmerged investigation, not authorization to merge, deploy or release.
