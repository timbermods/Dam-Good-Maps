# Applicability to stacked-layer water

`investigation/terrain3d` was absent from the remote branch listing when the follow-up was read. This is an architectural assessment of the current heightfield solver and the requested cave-below/ground-above scenario, not a measured result for an unseen 3D implementation. The branch check is recorded in `results/terrain3d-reference.json`.

The present solver has one floor, depth and contamination value per `(x,y)` tile, four horizontal outflows, and eight horizontal wet neighbours. Two vertically separated water bodies at the same `(x,y)` cannot share that state or its neighbour tests. A stacked solver needs distinct water cells/compartments and explicit connections, with ceilings and vertical transfers represented by its own rules. Its reference implementation must establish the new operation order before optimizing it. Matching today's 2D output is not a proof of correctness for those new rules.

The newer exact-cycle reference is also a heightfield model: its constructor rejects roofed-water objects such as `NaturalOverhang`. It is not an available stacked-layer oracle.

| Prototype | What carries over | What does not carry over unchanged |
|---|---|---|
| Neighbour-index table | Strongest transferable idea: cache immutable connectivity separately from water state. Preserve the reference's face/edge ordering. | `i ± W`, `i ± 1` and exactly four entries per tile assume one surface. A face may connect to zero, one or several overlapping layers. Use ordered adjacency and explicit reverse-edge indices; rebuild them when edits open/close connections. Preserve boundary kinds: an open map edge is not a sealed rock face. Do not cache changing water surfaces, wetted apertures or source strengths. |
| Directional-loop expansion | A fixed, small stencil can be expanded in exactly the reference order, with the same expressions and sums. | Four horizontal blocks cannot cover arbitrary layer-to-layer or vertical connections. Variable-length face lists may be better left as loops. Adding, sorting or grouping connections changes arithmetic order and needs a new proof. No speedup from the current unroll is transferable numerically. |
| Interior saturation fast path | Explicit integer wet-neighbour counts can help where a layer has the same proven local stencil. Integer counts remain exact. | The flat eight-index neighbourhood would mix cave and surface water or count water behind rock. “Interior” must be defined for the layer's connectivity, not merely map bounds. Roofed evaporation and soil contact cannot be inferred from a surface wet mask. Reuse the idea only after defining the stacked model's saturation/evaporation rules. |
| Skip redundant flow clearing | The general write-before-read argument survives: a slot need not be cleared if every path overwrites it before any read. | Being wet is not enough to establish that invariant for a cell with changing face lists, inactive layers, vertical transfers or closed apertures. Retired edges and wet-to-dry transitions still need zeros. This prototype has no useful standalone gain even in 2D, so it is a low priority. |
| Per-pool drought drop | Reusing an identical binary64 expression is safe when its inputs and pool membership remain fixed and the expression is genuinely common to all affected cells. | The existing uniform drop `(sum evaporation / tile count) × days` is a heightfield pool model. A roofed chamber has different evaporation exposure; storage area can change when water crosses floors, ceilings or connections. The current flood/pool solver and uniform-drop formula cannot simply be reused for stacked volumes. Derive that model first; hoist only expressions that its own reference repeats unchanged. |

The current neighbour table costs 16 bytes per water tile: 1 MiB at 256². With four entries per layer, that grows linearly with the number of represented layers; variable adjacency also needs offsets/counts and any face metadata. Benchmark sparse compartment layouts against dense per-voxel storage before choosing a layout. Those memory costs are representation arithmetic, not measured 3D performance.

The broader exactness discipline carries over fully: stable cell and face identifiers, fixed traversal and accumulation order, no fused/reassociated operations, no extra precision conversions, and byte comparisons of depth, contamination, momentum and intermediate state. The test set should include stacked pools sharing `(x,y)`, sealed caves, openings between layers, overflow between levels, roof changes, wet/dry edge activation and warm starts after topology edits. Compare Node and Chromium at substeps and checkpoints against the new stacked reference, then compare exported files. A region that looks settled is still not safe to freeze without a dependency proof covering every connected face, evaporation, source and contamination state.

Recommended order for a stacked implementation: define and test its reference semantics; establish stable ordered connectivity; evaluate a connectivity cache; then test fixed-stencil unrolling and layer-local saturation fast paths. Treat all current speedup numbers as 2D measurements only. This investigation makes no change to a terrain3d branch or production terrain representation.
